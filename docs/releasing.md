# Distribution and releasing

## Channels

| Channel | Command | Audience | Status |
|---|---|---|---|
| **Homebrew tap** (primary) | `brew install wearhats/tap/hats` | Most Mac developers; allowed on managed Macs where `curl \| sh` is blocked | Formula generated by `scripts/render-formula.sh`, pushed by the release workflow |
| **Install script** | `curl -fsSL https://wearhats.dev/install.sh \| sh` | No Homebrew | `scripts/install.sh`, attached to every release; the domain redirects to it (see below) |
| **Inspect, then run** | `curl -fsSLO …/install.sh && less install.sh && sh install.sh` | Cautious users | Same script |
| **Manual download** | `hats-macos-universal.tar.gz` from the Releases page | Air-gapped or scripted setups | Release asset |
| **From source** | `swift build -c release` | Contributors | README |
| **homebrew-core** | `brew install hats` | Everyone | Once the project meets homebrew-core's notability bar; core builds from source with Xcode |

Not planned: Mac App Store (the sandbox forbids reading other processes and
launching Claude with custom arguments), npm or pip wrappers (a runtime
dependency for a native binary), and a self-updater (Homebrew and the script
already update; a self-updater is more attack surface).

## The install script

`scripts/install.sh` is POSIX sh and shellcheck-clean.
- Refuses non-macOS and macOS older than 14.
- Downloads the release tarball and `SHA256SUMS` from the release, so the
  script is the one built for that release rather than whatever is on `main`.
- Verifies the SHA-256 and refuses to install on a mismatch.
- Verifies GitHub build provenance (`gh attestation verify`) when the GitHub CLI
  is installed and signed in, and says so when it skips the check.
- Installs to `~/.local/bin` (or `--dir`, `HATS_INSTALL_DIR`). No sudo, no
  edits to shell startup files; it prints the `PATH` line instead.
- The whole script runs from a `main` function called on its last line, so a
  download cut short by `curl | sh` runs nothing.
- `--version vX.Y.Z` pins a release. `HATS_BASE_URL` points at a mirror or a
  local directory (used by CI).

## The install URL

`https://wearhats.dev/install.sh` is a 302 redirect to
`https://github.com/wearhats/hats/releases/latest/download/install.sh`, not a
copy. The script users run is then always the one attached to the latest
release, with its repository name filled in, and the domain never serves
anything a release didn't build. Use a temporary redirect, because clients may
cache a permanent one. The long GitHub URL keeps working if the domain is down.

## Release assets

Each GitHub Release carries:
- `hats-macos-universal.tar.gz`: `hats` (arm64 + x86_64), `LICENSE`, `README.md`.
  The name has no version, so `releases/latest/download/…` links never change.
  The packaging is reproducible: for the same binary, `scripts/package.sh`
  writes a byte-identical tarball (mtimes from `SOURCE_DATE_EPOCH` or the
  commit time, fixed entry order, owner and group 0, fixed modes, no extended
  attributes or AppleDouble files, `gzip -n`). The binary is not bit-for-bit
  reproducible across toolchains, and a Developer ID signature carries a
  timestamp, so only the packaging step is deterministic.
- `SHA256SUMS`.
- `install.sh`, with the repository name filled in.
- A build provenance attestation (Sigstore, through `actions/attest-build-provenance`).

## Signing and Gatekeeper

- **With a Developer ID** (the goal before 1.0): hardened runtime, timestamped
  signature, notarized with `notarytool`. A bare binary can't be stapled, so
  Gatekeeper checks notarization online the first time a quarantined copy runs.
- **Without one** (until the project has an Apple Developer account): ad-hoc
  signature. Homebrew and `curl` downloads carry no quarantine flag, so the
  binary runs. A browser download is quarantined; the README documents
  `xattr -d com.apple.quarantine hats`.
- Launcher bundles are generated on the user's Mac, never downloaded, so they
  carry no quarantine flag either.

## Upgrades and uninstall

- `brew upgrade hats`, or re-run the install script. hats checks GitHub for a
  newer release once a day and prints a notice with the upgrade command; it
  never upgrades itself. `hats doctor` names the same command: Homebrew installs are
  recognized by their `Cellar` path, script installs by the
  `$HATS_HOME/install.json` receipt that `install.sh` writes.
- Launchers record the `hats` path they call. Homebrew's
  `$(brew --prefix)/bin/hats` symlink and `~/.local/bin/hats` stay the same
  across upgrades, so launchers keep working. After moving between channels,
  `hats launcher rebuild` repoints them. Doctor fails on a launcher whose
  `hats` is missing, and warns on one that calls a different `hats` from the
  one on `PATH`.
- Uninstall: `hats rm --all --purge` (optional), then `brew uninstall hats` or
  `rm ~/.local/bin/hats`, then remove `~/Applications/Hats`.

## Architectures

Universal (arm64 + x86_64) while the CI toolchain can link x86_64, because
macOS 14 to 26 still run on Intel Macs. The macOS 27 Command Line Tools no
longer ship x86_64 Swift runtime libraries, so local universal builds fail
there. When CI loses x86_64 too, releases become arm64-only and the asset name
stays the same.

## Versioning and the release flow

SemVer, `0.x` until the command set is stable. Conventional Commits.
[release-please](https://github.com/googleapis/release-please) keeps a release
PR open on `main` that bumps `Sources/hats/Version.swift` and writes the
changelog. Merging it runs `.github/workflows/release.yml`:

1. **release-please**: tag `vX.Y.Z` and create the GitHub Release as a
   **draft** (`draft` and `force-tag-creation` in `release-please-config.json`;
   a draft otherwise has no tag yet).
   0.1.0 is the exception: it was tagged `hats-v0.1.0`, before
   `include-component-in-tag` was turned off, and published releases can't be
   retagged. `last-release-sha` points release-please at it until the next
   release exists.
2. **build** (`contents: read`, no secrets): build the universal binary on
   the `xcode-27` runner with the pinned Xcode, check `hats --version` matches the tag,
   and hand the unsigned binary to the next job as a workflow artifact.
3. **publish** (`contents: write`, `id-token: write`, `attestations: write`),
   which never builds or runs the binary:
   1. Sign and notarize (or ad-hoc sign without secrets).
   2. Package with `scripts/package.sh` and write `SHA256SUMS`.
   3. Attest build provenance.
   4. Upload the tarball, `SHA256SUMS` and `install.sh` to the draft.
   5. Un-draft the release (`gh release edit --draft=false --latest`). Until
      this step, `releases/latest/download/…` still serves the previous
      release, so it never returns a 404 for a release without assets.
4. **homebrew-tap** (`contents: read`, plus an App token for
   `wearhats/homebrew-tap` only): render `Formula/hats.rb` with the SHA-256
   from the published `SHA256SUMS` and push it to the tap. This runs after
   un-drafting because draft assets aren't publicly downloadable, so the
   formula's URL only works once the release is public.
   The tap can't be fixed before the release is public, so every CI run checks
   the formula first: `just package` renders it and `scripts/check-formula.sh`
   runs `brew style` and `brew audit --strict` on it in a throwaway tap.

Splitting build from publish keeps the write-scoped token, the OIDC token and
the signing secrets out of the job that runs package code (SwiftPM plugins and
dependencies). Every checkout uses `persist-credentials: false`.

The organization enforces immutable releases: once a release is published,
its assets and tag can't change. To recover from a failed run, use **Re-run
failed jobs**:
- **publish failed**: the release is usually still a draft, where assets can
  still be replaced, and `--clobber` makes the upload repeatable. If it was
  already un-drafted, publish skips every step, so nothing is re-signed,
  re-attested or re-uploaded, and homebrew-tap still runs.
- **homebrew-tap failed**: the release is already public, and only this job
  runs again. It reads the checksum from the published release, and does
  nothing if the formula is already at that version.

Don't use **Re-run all jobs**. release-please runs again, finds no release
pending because the merged release PR is already tagged, and build, publish and
homebrew-tap are all skipped.

A broken published release can't be repaired in place: release a new patch
version.

CI runs the build, packaging and install script on every PR (installing from a
local `file://` release), and checks the rendered formula's Ruby syntax.

### Toolchain

Both workflows run on the `xcode-27` runner image and select
`/Applications/Xcode_27.1.app` (`XCODE_APP` in `release.yml` and `ci.yml`),
which ships Swift 6.4, the toolchain development uses. It must exist on the
image (see the actions/runner-images README). Bump it when the image drops it
or a newer Swift is wanted, in both files at once, and note the Xcode version in the
release notes: the binary is only reproducible with the same toolchain.

### Changelog

release-please owns `CHANGELOG.md` from the first release onward. It writes
each released section from the Conventional Commit messages, so contributors
don't hand-edit released sections. Fix a wrong entry by editing the release PR
before merging it, or the GitHub Release notes afterwards.

Commits that only touch `site/` (the project website) are excluded
(`exclude-paths`), so website changes never bump the version or appear in the
changelog.

### Secrets

Release credentials live in the `release` environment on `wearhats/hats`
(deployment branches: `main` only). Every job that reads them declares
`environment: release`.

| Name | Kind | Used for |
|---|---|---|
| `RELEASE_APP_CLIENT_ID` | variable | Client ID of the `wearhats-release` GitHub App |
| `RELEASE_APP_PRIVATE_KEY` | secret | That App's private key (`.pem` contents) |
| `APPLE_DEVELOPER_ID_P12`, `APPLE_DEVELOPER_ID_PASSWORD` | secret | Developer ID Application certificate (base64 `.p12`) |
| `APPLE_NOTARY_KEY_ID`, `APPLE_NOTARY_ISSUER`, `APPLE_NOTARY_KEY_P8` | secret | App Store Connect API key for `notarytool` |

`wearhats-release` is an organization-owned GitHub App (Contents read and
write, Pull requests read and write, Metadata read), installed on `hats` and
`homebrew-tap` only. No personal access tokens are involved: each job mints its
own installation token with `actions/create-github-app-token`, scoped to one
repository and expiring within an hour:
- release-please: `hats`, contents and pull requests write. PRs opened with an
  App token trigger CI, unlike those opened with `GITHUB_TOKEN`.
- homebrew-tap: `homebrew-tap`, contents write. Its commits are authored by
  `wearhats-release[bot]`.

The workflows also use the built-in `GITHUB_TOKEN` (`github.token`) for
uploading assets, un-drafting the release and reading it back.

The App is required to release from `wearhats/hats`. The organization doesn't
let `GITHUB_TOKEN` create pull requests, so without the App the release-please
job fails whenever it has a release PR to open. The `github.token` fallback is
for forks that allow this; their release PRs get no CI checks, because GitHub
doesn't trigger workflows from events that token creates (push an empty commit
to the release branch, or close and reopen the PR, to run them). Without the
App, the homebrew-tap job warns and the tap is updated by hand.

The Apple secrets are optional. Without them the release is ad-hoc signed.

## Release gate: verified on Claude Desktop X / Claude Code Y

hats depends on Claude Desktop and Claude Code internals it doesn't control
(`--user-data-dir`, `CLAUDE_CONFIG_DIR`, `sessions/*.json`). A release is not
merged until it records the versions it was verified against:

- [ ] Re-run `scripts/compat-check.sh` against the current Claude Desktop and
      Claude Code, and re-check the "Not verified yet" items in the
      [platform notes](architecture.md#8-platform-notes). The script prints the
      Claude Desktop version; get the Claude Code one with `claude --version`.
- [ ] Put "Verified on Claude Desktop X, Claude Code Y, macOS Z" in the release
      notes (edit the release PR body or the draft release).
- [ ] Update the README's "Tested with" line to the same versions.

## Manual checklist (minor releases)
- [ ] The release gate above, including the sign-in steps `compat-check.sh` pauses for.
- [ ] Fresh macOS user account: install through both `brew` and the script,
      `hats setup`, click the launcher, sign in, `hats ps`, `hats rm --all --purge`.
- [ ] `hats dock pin` and `hats dock unpin` on a real Dock.
- [ ] `hats doctor` is clean on a maintainer's Mac.
